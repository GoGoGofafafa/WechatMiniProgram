# 城镇商家个体户记账小程序：产品方案与技术设计

## 1. 目标与范围

本项目面向小商户（如乡镇家电店、杂货店、建材店等），用于管理“赊账/借账—还款”流水，减少纸质账本丢失、查找困难、统计麻烦的问题。

你提出了三个场景：

- **场景 B（MVP，优先）**：手动录入借账信息、可改可删、同一借款支持多笔还款；支持按地址/金额筛选排序、按姓名搜索。
- **场景 A（第二阶段）**：拍照纸质账本，OCR 识别并上传借账信息（姓名、地址、借款金额、借款日期、还款日期、还款金额）。
- **场景 C（第三阶段）**：借款与门店消费订单挂钩（如购买冰箱+空调总额5000，实付3000，赊账2000）。

建议路线：

1. 先完成 **场景 B** 跑通全链路（页面、数据、筛选、搜索、统计）。
2. 再接入 **场景 A OCR**，将拍照结果进入“待确认”流程，人工校对后入库。
3. 最后补齐 **场景 C**（消费单与借款关联），形成完整经营闭环。

## 2. MVP（场景 B）功能清单

### 2.1 借账管理

每条借账信息字段：

- 借款人姓名（必填）
- 地址（可选但建议填写）
- 借款金额（必填）
- 借款日期（必填）
- 备注（可选）

操作：

- 新增借账
- 编辑借账
- 删除借账（建议二次确认）
- 查看借账详情

### 2.2 还款管理（挂在借账下）

每条还款信息字段：

- 还款日期（必填）
- 还款金额（必填）
- 还款方式（现金/微信/支付宝/转账，可选）
- 备注（可选）

规则：

- 一条借款可对应多条还款。
- 实时计算：
  - 累计还款金额
  - 剩余应还金额 = 借款金额 - 累计还款
  - 状态：未还清 / 已还清 / 超额还款（异常标记）

### 2.3 列表筛选与搜索

借账列表支持：

- **按地址过滤**（如“东街”“南村”）
- **按金额区间过滤**（如 0~500、500~2000、2000+）
- **按金额排序**（升序 / 降序）
- **按借款日期排序**（最新/最早）
- **按姓名搜索**（支持模糊匹配）

### 2.4 基础统计（推荐作为 MVP 增强）

- 总借出金额
- 总已还金额
- 总待还金额
- 逾期笔数（若启用预计还款日）

## 3. 小程序信息架构（MVP）

建议页面结构：

1. **首页/总览页**
   - 关键统计卡片（总借出、总已还、待还）
   - 最近借账记录
2. **借账列表页**
   - 搜索框（姓名）
   - 筛选器（地址、金额区间）
   - 排序按钮（金额、日期）
3. **借账编辑页（新增/修改）**
4. **借账详情页**
   - 基本信息
   - 还款记录列表
   - “新增还款”按钮
5. **还款编辑弹窗/页面**

## 4. 数据模型设计

> 采用“借款主表 + 还款子表”的一对多结构。

### 4.1 Loan（借款）

- id: string（主键）
- borrowerName: string
- borrowerAddress: string
- principalAmount: number
- loanDate: string (YYYY-MM-DD)
- expectedRepayDate: string | null
- note: string | null
- createdAt: number（时间戳）
- updatedAt: number（时间戳）

### 4.2 Repayment（还款）

- id: string（主键）
- loanId: string（外键 -> Loan.id）
- repayDate: string (YYYY-MM-DD)
- repayAmount: number
- repayMethod: string | null
- note: string | null
- createdAt: number
- updatedAt: number

### 4.3 LoanAggregate（可实时算，也可缓存）

- totalRepaid: number
- remainingAmount: number
- status: UNPAID | PAID | OVERPAID

---

## 5. 核心业务规则

1. 借款金额、还款金额都必须 > 0。
2. 删除借款时，默认级联删除其还款记录（或采用软删除）。
3. 还款总额超过借款金额时标记 OVERPAID，需在 UI 高亮提醒。
4. 所有金额统一用“分”存储（整数）以避免浮点误差；展示时再转元。
5. 所有时间统一存储 ISO 日期字符串（YYYY-MM-DD）。

## 6. 技术实现建议（微信小程序）

## 6.1 前端

- 框架：原生小程序 / Taro（二选一，建议先原生快速上线）。
- 状态管理：页面局部状态 + 轻量全局 store（如 MobX/miniprogram-store）。
- 组件：
  - 搜索框组件
  - 筛选抽屉组件
  - 借账卡片组件（显示姓名、地址、借款、已还、待还、状态）

## 6.2 后端

可选方案：

1. **微信云开发（推荐起步）**
   - 优点：部署快、登录与存储打通、适合 MVP。
2. 自建后端（Node.js + MySQL/PostgreSQL）
   - 适合后期做复杂权限、跨平台等。

## 6.3 API（示例）

- `POST /loans` 新增借款
- `PUT /loans/:id` 修改借款
- `DELETE /loans/:id` 删除借款
- `GET /loans` 列表（支持 query: name, address, minAmount, maxAmount, sortBy, sortOrder）
- `GET /loans/:id` 借款详情
- `POST /loans/:id/repayments` 新增还款
- `PUT /repayments/:id` 修改还款
- `DELETE /repayments/:id` 删除还款

## 7. 场景 A（OCR）二期方案

目标：从账本照片中抽取结构化数据并入库。

流程建议：

1. 用户拍照/上传账本图片。
2. 后端调用 OCR（微信 OCR / 腾讯云 OCR / 第三方 OCR）。
3. 通过规则或 LLM 对 OCR 文本进行结构化解析：
   - 姓名
   - 地址
   - 借款金额
   - 借款日期
   - 还款日期（可多条）
   - 还款金额（可多条）
4. 输出“**待确认草稿**”而不是直接入库。
5. 用户人工校对后一键保存。

关键点：

- OCR 识别准确率不稳定，必须有“人工确认”环节。
- 保留原图与识别结果，便于追溯。
- 对金额/日期增加格式校验与异常提示。

## 8. 场景 C（消费挂钩）三期方案

新增实体 `SaleOrder`（销售单）：

- orderId
- customerName
- items（商品明细：冰箱、空调等）
- totalAmount（应付）
- paidAmount（实付）
- creditAmount（挂账/借款 = total - paid）
- saleDate

关联策略：

- 创建销售单时，如果 `creditAmount > 0`，自动创建/关联一条 Loan。
- Loan 中新增 `sourceType = SALE_ORDER`、`sourceId = orderId`。
- 在借款详情中展示“来源订单”，可跳转订单详情。

这样就能清楚回答：

- 哪些借款来自真实交易
- 哪些是纯现金借款
- 某客户消费与欠款的整体关系

## 9. 里程碑与排期建议

### 里程碑 1（1~2 周）

- 场景 B 完成：借款 CRUD、还款 CRUD、筛选排序搜索、基础统计。
- 可供 1~3 家门店试用。

### 里程碑 2（1~2 周）

- OCR 上传 + 待确认草稿流。
- 支持单张账本页识别入库。

### 里程碑 3（2 周）

- 消费订单模块 + 借款关联。
- 提供按客户维度的经营报表。
